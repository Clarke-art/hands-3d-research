## 0. 本轮一句话结论

> ## 推荐：`ROUTE_C`（共享 3D 母体来自**人工作者化网格**）+ `ROUTE_B` 作为**受限并行实验**
>
> `RECOMMENDED_SHARED_3D_BOOTSTRAP_ROUTE = ROUTE_C_PRIMARY (CC0 AUTHORED BASE MESH) + ROUTE_B_PARALLEL_BOUNDED_EXPERIMENT`
>
> 理由一句话：**本项目要的是"结构正确、可 Rig、可长期复用的 Piano Hand Master"。这三条都不是 AI 生成器的强项，而是人工作者化网格的强项；且本项目在 Stage 4 / Stage 5 本来就有人工 3D 环节，改用作者化基础网格不会新增技能需求，只会把人工从"修复 AI 缺陷"转移到"造型与拓扑"。**

**关键认知（本轮最重要的发现）**：

> 🎯 **AI 可以从输入图近似继承姿态，但无法可靠、可审计地保证符合冻结的 RSSF 技术范围**（`HR-06b` / `HR-06c`）。
> 因此 **最终 RSSF 必须人工验证，必要时在 Blender 中重新摆姿**。
>
> 在此前提下，各路线真正的差别主要在两件事：
> 1. **解剖是否正确**；
> 2. **拓扑是否为变形而设计**。
>
> 谁能在这两件事上更可靠，谁就更适合做长期母体。**构图的自动化程度不是评价标准。**

## 1. 承接 Stage 1A 的 FAIL 结论（不重开）

### 1.1 已冻结的判定

| 项 | 值 |
| --- | --- |
| `AI_MULTIVIEW_FEASIBILITY` | **`FAIL`** |
| 失败路线 | 2D Anchor → AI 图像编辑 → 派生 DORSAL / PALMAR / RADIAL / ULNAR |
| `2D_IMAGEGEN_MULTIVIEW_ROUTE` | **`REJECTED_BASELINE`** |
| 是否重开 | 🚫 **不得重开** |

### 1.2 失败机制的形式化（本轮承接，不重测）

Stage 1A 的四条缺失是**结构性**的，不是提示词工程问题：

| 缺失 | 后果 |
| --- | --- |
| 无共享 3D geometry | 每次图像编辑都**重新采样**手部几何，而不是同一几何的重投影 |
| 无固定 camera extrinsics | 无法证明"只移动相机"，也无法反解深度 |
| 无固定 world lighting | `LIGHT = FIXED` 不可证明，只能声称 |
| 无固定 Pose 参数 | 半屈曲/张开度在每张图上重新"猜"一次 |

→ **只要生成管线的中间表示是 2D 位图，上述四条在原理上都不可能满足。**
→ 因此本轮的起点改为：**先获得一个统一 3D 母体（ONE_SHARED_3D_GEOMETRY），再让所有视角来自这个共享几何。**

### 1.3 本轮的直接收益预告

值得注意：**`ROUTE B` 在"同一几何一致性"这一项上是满分的**——单图生成的产物**本身就是一个 mesh**，"唯一 3D 对象"这件事由构造保证。
**问题的性质因此发生了转移**：从"多视角是否一致"变成了"**单一网格的不可见区域是否正确**"。
这是本轮的判断重心。

### 4.3 🔴 A‑2 的结构性问题：**授权与"Web 分发"天然冲突**

这不是某一家的个别条款，而是**整个商业素材市场授权模型的共性**：

| 事实 | 后果 |
| --- | --- |
| 本项目交付物是**在浏览器里运行的交互资产**，Three.js 必须把 `.glb` 下载到终端用户设备 | 从技术上，**模型文件必然到达最终用户** |
| 商业素材市场的 RF 授权**普遍禁止**"再分发模型文件、或其衍生的 3D 格式"（3D Scan Store 明确写：*Resale or public sharing of the scan or any derivative of the scan in any 3d format*） | 交付场景与该条款**存在实质冲突** |
| 各平台的 "single commercial project" 档位允许"集成进一个对外销售的商业项目"，但对"用户可提取模型文件"这一情形**通常没有明确表述** | 属于**灰区**，不能靠自我解读通过 |

> ⚠ **`LIC-01`（HIGH）**：任何 A‑2 候选在进入母体路线前，**必须取得供应商的书面澄清**：
> "该资产经修改/重拓扑/重新绑定后，作为 **Web 交互式数字教材中可被终端用户下载的 GLB** 分发，是否需要额外授权档位？"
> **未获得书面澄清前，A‑2 只能降级为"形状与比例参照"（不进入交付物）。**

> 📌 这一条单独就足以解释为什么 **A‑2 不能作为首选**：它在本项目的优先级排序中，卡死在"**授权安全**"这一项上（第 4 优先级）。

## 5. ROUTE B · `A02` → Hunyuan3D 单图生成

### 5.1 技术可行性：**成立**

已核实 `HY-3D-3.1` 接口支持**纯单图输入**（`ImageUrl` / `ImageBase64` / `Prompt` 三者取其一即可），
且 **Model 3.1 下 `LowPoly` 不可用**；官方参数枚举仍列有 `Sketch`，但本项目在本轮实验中禁止使用（`PROHIBIT_SKETCH_FOR_THIS_EXPERIMENT`，见配套合同 §2）。
可用 `GenerateType = Geometry`（白模）+ `FaceCount` 控制面数。
→ **"用 A02 直接生成 3–4 个 3D Candidate"在技术上没有障碍。** 相关参数见配套合同文档。

### 5.2 ⚠ `A02` 的实际观测覆盖：**这是一个量化问题，不是一个感觉问题**

本轮已对 `references/hand_r_canonical_ai/anchor/ANCHOR_A02_PRECHECK.png` 逐面检查：

| 项 | 观测 |
| --- | --- |
| 视角 | **掌背（DORSAL）+ 桡向斜视**（约 35–45° 偏桡侧） |
| 可见面 | 手背、五指背侧全长、指甲、**拇指桡侧与背侧**、腕部、短前臂 |
| **不可见面** | 🔴 **整块掌心面**：大小鱼际、掌横弓/纵弓、掌侧皮纹、**五指掌侧全长**、**掌侧指蹼（web space）**、指腹 |
| 定量估计 | 手掌与手指的**掌侧表面约占整只手表面面积的 40–50%**，在本图内**观测覆盖率 = 0** |
| 图像级标定 | 无相机外参、无尺度参照 → **无法从该图反解关节角**，`HR-06b` / `HR-06c` 的技术范围无法在图层面被验证或施加 |

**结论**：ROUTE B 的核心风险不是"AI 画得好不好"，而是——

> 🔴 **掌侧近一半的表面在输入中完全不存在，必须由模型"发明"。**
> 而 `G-03`（拇指非猿手）、`G-05`（掌弓）、`G-04`+`T-03`（指蹼与指缝独立）、
> `G-06`（指尖触键点）——**这四项恰好全部落在掌侧**。

### 5.3 Hunyuan3D 单图的已知输出特性（影响下游）

| 特性 | 对本项目的影响 |
| --- | --- |
| 输出为**三角面、无拓扑控制** | `T-06` 已规定"必须 Retopo"，此项本来就不可避免；但**无 edge flow 的重拓扑比有 edge flow 的重拓扑更费工** |
| 3.1 在**有机形体**上表现最好，在**硬表面**上较弱 | 手属于有机形体 → 相对有利 |
| **非确定性**（无 seed 固化；同输入不保证同输出） | ⚠ 母版资产**不可复现/不可审计**。母体一旦确定必须冻结文件，无法"再生成一次一样的" |
| 已知失败模式：**手指融合（fused digits）** | 直接对应 `G-04` / `T-03`，是手部 AI 生成的头号缺陷 |
| 官方 `FaceCount` 范围为 **3000–1500000**（默认 500000）；本实验固定 **100000 = `PROJECT TEST VALUE`**，**不是接口最低值** | 相对本项目 8k–20k 目标偏重，但经 Retopo 后可控 |

### 5.4 ROUTE B 的定性判定

| 维度 | 判定 |
| --- | --- |
| 是否技术可行 | ✅ 是 |
| 是否解决"同一几何一致性" | ✅ **是**（由构造保证，单图只产出一个 mesh） |
| 是否解决"掌心结构" | ❌ **不保证**，且输入中无任何掌心信息 |
| 是否是最便宜的"信息实验" | ✅ **是**（成本极低、可立刻执行） |
| 是否可作为**唯一**母体来源 | ❌ **不建议** |

→ **ROUTE B = `CONDITIONAL`**：**适合作"AI 手部几何能达到什么水平"的低成本探测实验**，
**不适合作"不需要人工重造型与重拓扑"的免人工方案**。

### 6.2 为什么 ROUTE C 在**本项目优先级**下胜出

项目给定的优先级：

> **结构正确 > 可 Rig > 变形稳定 > 授权安全 > 可复用 > Web 性能 > 生产成本**

按这个顺序逐项看：

| 优先级 | ROUTE C（C-1 / C-2） | ROUTE B |
| --- | --- | --- |
| 1 结构正确 | 人工作者化网格，比例与结构由作者保证；缺失的只有姿态与环线密度 | **掌侧 40–50% 表面是发明的** |
| 2 可 Rig | 四边面通用拓扑，**为后续处理而设计** | 三角面、无 edge flow，**必须全量重拓扑** |
| 3 变形稳定 | 可追溯到既有行业拓扑惯例 | 不可预测，`T-01`/`T-03`/`T-04` 全部待验证 |
| 4 授权安全 | **CC0 = 满分** | 需付费档位；AI 生成物权利归属需另行确认 |
| 5 可复用 | 母体文件静态、可版本化、可审计 | **非确定性**，不可复现 |
| 6 Web 性能 | Retopo 后完全可控 | Retopo 后可控（但重拓扑工时更高） |
| 7 生产成本 | 低（资产 0 元） | **最低**（单次生成成本极低） |

→ **ROUTE C 在第 1–5 项全部领先，只在第 7 项落后。**
→ 而第 7 项是本项目**明确的最低优先级**。
→ **判定：`ROUTE_C = VIABLE`。**

### 6.3 一个必须澄清的常见误解

> ❓ "选 ROUTE C 是不是等于 WorkBuddy 自己在 Blender 里手搓一只手？"
>
> ❌ **不是。** ROUTE C 是：
> **获取一个已经存在的、许可干净的、有解剖依据的、四边面的人工作者化网格 → 由 3D 资产方把它造型到 RSSF 并核验/补拓扑 → 进入既有的 Stage 5 Rig。**
>
> 这道工序**原本就在流水线里**（Stage 4 Blender Engineering：清理 → Retopo → UV → 形态修正）。
> ROUTE C 改变的只有一件事：**Stage 2 的几何来源**从"Hunyuan3D 多视角重建"换成"授权的作者化基础网格"。
> **WorkBuddy 在本项目中的职责边界不变**（规范制定 + 校验 + 运行层集成，不做模型生产）。

## 8. 专项判断：是否还需要"8 图再进混元"

> 问题：若 `A02 → Hunyuan3D 单图 → 得到一个质量足够好的统一 3D Hand Candidate`，
> 是否还有必要 `3D Candidate → 渲染 8 Views → 再次提交 Hunyuan3D Multi-view`？

### 8.1 结论（先给答案）

> ## ❌ **不默认需要。**
> ## 并且：**不要把"候选自己渲染的 8 张图"喂回多视角重建。**
>
> `STAGE1B_8VIEW_REFINEMENT = NOT_RECOMMENDED_AS_DEFAULT`
> `SELF_RENDERED_8VIEW_REFEED = PROHIBITED_AS_RESCUE_PATH`

### 8.2 CASE 1 — 单图 3D 几何已经足够好

**判定**：`单图 3D 几何已达标` → **直接进入**：

```
Geometry Review（GATE 2，人工）
  → Blender Engineering（Stage 4：清理 / 造型到 RSSF / Retopo / UV）
  → Rig（Stage 5）
```

**理由**：此时"再造 8 视角"不产生任何新的几何信息，只产生流程开销与新的失真风险。
**此时 `8VIEW_REFINEMENT = NOT_NEEDED`。**

### 8.3 CASE 2 — 单图 3D 的掌心 / 指蹼 / 拇指明显不足

这里必须做出一个**本轮最重要的技术判断**：

> ### 🔴 把候选自己渲染出的 8 张图再喂回多视角重建，**在原理上不可能补回掌心**。

三条理由：

| # | 理由 | 说明 |
| --- | --- | --- |
| **① 信息论** | 自渲染的 8 张图**不包含任何关于掌心的新观测**。候选的掌侧本来就是猜的；把猜测渲染 8 遍，回炉后仍然是同一个猜测。**没有新的观测通道，就没有新的信息。** |
| **② 反向强化（最危险）** | 多视角重建器会把**多张彼此一致**的视图当作**强证据**。自渲染的 8 图几何上完全自洽（它们本来就来自同一个 mesh），于是重建器会**把原有的错误几何当成高置信度事实固化下来**，同时抹平原有的表面细节。**结果是"错误 + 更光滑"。** |
| **③ 该方案的收益上限很低** | 即使在可见面上，自渲染多视角能带来的也只是"表面正则化"，而这一点在下一步的人工 Retopo 里会被完全重做。**收益落在会被丢弃的那一层上。** |

**行业侧的反面印证（多视角输入的基本规律）**：

- 共识是"**互相矛盾的视角比更少的视角更糟**"——多视角重建器会把冲突"平均成一团糊"。
- 由此可直接推出本轮的判断：**自渲染视角虽然"不矛盾"，但它的代价是②（把幻觉升级成事实）。**
  这两种情形都不是我们想要的。
- 同时也顺带印证了 Stage 1A 的 FAIL：**Stage 1A 的 4 张 AI 派生图恰恰是"互相矛盾"的那一类**，
  若当时把它们送进多视角重建，结果只会比单图更差。这为"不重开 2D 路线"提供了额外的独立理由。

### 8.4 那么"8 视角"在什么条件下才真正有意义？

> ✅ **只有一个条件：8 个视角来自对同一只手的真实观测。**
> （或来自一个**已被人工确认解剖正确**的共享母体，且目的仅为**表面细节/纹理规范化**。）

| 8 视角的来源 | 是否可用于多视角重建 | 说明 |
| --- | --- | --- |
| 真人同一次采集（`HAND=FIXED / LIGHT=FIXED / CAMERA=MOVES`） | ✅ **是**，这是**唯一**合规的补盲手段 | 即 Stage 1 的原始任务，**没有被废除** |
| AI 逐视角派生（Stage 1A 路线） | ❌ **否** | `REJECTED_BASELINE` |
| **候选自己渲染的 8 图** | ⚠ **仅可作为一次性受控 A/B 实验**，**不得作为缺陷救援手段** | 见 8.3② |

### 8.5 对选择 ROUTE C 的连带说明

若采纳 ROUTE C，**"8 视角"不但不浪费，反而回到了它真正该承担的角色**：

| 8 视角在 ROUTE C 下的用途 | 说明 |
| --- | --- |
| **比例与解剖校验** | 用真人参考校验 `ADULT_NEUTRAL` 的手长/掌宽/指长比（不是重建输入） |
| **纹理来源** | 基础网格无贴图；semi-realistic 材质需要真实皮肤参考 |
| **教学对比参照** | 腕部三态（过高/中立/过低）等的视觉参照 |
| **人工造型的判据** | "造型到 RSSF"时的人工比对基准 |

→ **`STAGE1_REFERENCE_ACQUISITION = RETAINED_BUT_RESCOPED`**（保留，但角色从"重建输入"变为"校验与纹理基准"）。
